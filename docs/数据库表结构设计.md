# 优学课堂数据库表结构设计

## 1. 文档信息

- 文档版本：v0.1
- 更新时间：2026-03-23
- 关联文档：
  - `docs/项目设计规范.md`
  - `docs/API接口清单.md`
  - `docs/后台管理系统页面原型清单.md`
- 文档目标：定义首版可直接开发的数据库表结构、字段约束、索引策略和实体关系，为后端开发、接口实现和初始化数据准备提供统一基线

## 2. 技术假设

本表结构设计默认基于以下技术假设：

- 数据库：`MySQL 8.0`
- 存储引擎：`InnoDB`
- 字符集：`utf8mb4`
- 排序规则：`utf8mb4_unicode_ci`
- 时间字段：优先使用 `DATETIME`
- 主键策略：优先使用 `BIGINT UNSIGNED`
- API 输出时，所有 ID 建议序列化为字符串返回前端

如后续改为 PostgreSQL，字段类型和索引语法需要做少量调整，但实体关系和字段语义可保持不变。

## 3. 设计原则

### 3.1 范围原则

首版仅覆盖以下核心业务：

- 管理员登录与角色权限
- 用户管理
- 课程管理
- 会员激活码体系
- 资源上传与多存储配置
- 系统设置与审计日志

明确不纳入首版：

- 第三方支付
- 订单和退款
- 多租户
- 复杂审批流

### 3.2 建模原则

- 业务主表使用自增 `BIGINT UNSIGNED` 作为内部主键。
- 对外展示编号可另行定义业务编号字段，如 `user_no`、`course_no`、`batch_no`。
- 高频查询字段必须建立普通索引或联合索引。
- 日志表原则上不做软删除。
- 业务主表尽量保留 `status` 字段，避免直接物理删除。

### 3.3 关系策略

首版建议采用“逻辑外键 + 索引约束”为主：

- 在应用层保证关联对象存在性。
- 数据库层优先保证唯一索引、普通索引和业务约束。
- 配置类、关系类表可按团队偏好补物理外键，但不是首版阻塞条件。

这样做的原因是：

- 迁移和迭代更轻。
- 后续拆服务或批量导入时更灵活。
- 更符合当前 MVP 阶段的开发节奏。

## 4. 命名与通用字段规范

### 4.1 命名规范

- 表名统一使用复数：如 `users`、`courses`
- 字段名统一使用 `snake_case`
- 状态字段统一命名为 `status`
- 创建时间统一命名为 `created_at`
- 更新时间统一命名为 `updated_at`
- 软删除时间统一命名为 `deleted_at`

### 4.2 通用字段建议

除日志表和纯关系表外，业务表默认建议包含以下通用字段：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `id` | `BIGINT UNSIGNED` | 主键 |
| `created_at` | `DATETIME` | 创建时间 |
| `updated_at` | `DATETIME` | 更新时间 |
| `deleted_at` | `DATETIME NULL` | 软删除时间，可选 |

### 4.3 状态值约定

建议统一采用字符串状态，降低可读性成本：

| 场景 | 建议值 |
| --- | --- |
| 通用启停 | `enabled` / `disabled` |
| 课程状态 | `draft` / `published` / `offline` |
| 会员状态 | `normal` / `active` / `expired` / `permanent` |
| 激活码状态 | `unused` / `used` / `expired` / `invalid` |
| 账号状态 | `normal` / `frozen` / `canceled` |

## 5. 核心实体关系总览

核心关系如下：

- 一个管理员可拥有多个角色。
- 一个角色可拥有多个权限点。
- 一个用户对应一条当前会员快照，可拥有多条会员变更记录。
- 一个会员套餐可生成多个激活码批次。
- 一个激活码批次可生成多个激活码。
- 一个用户可兑换多个激活码，但单个激活码只能被一个用户成功使用一次。
- 一门课程可关联多个专题标签。
- 一门课程可拥有多级章节与课时结构。
- 一个课时可关联视频和讲义资源。
- 所有封面、视频、文档统一落在资源表中。

## 11. 当前结论

按本设计即可直接开始后端开发，首版不会被表结构阻塞。需要特别注意的 3 个实现点：

1. 激活码兑换必须做幂等，建议依赖 `activation_redeem_logs.request_id`。
2. 课程发布前要校验课时与资源完整性，避免空课程上线。
3. 存储配置默认驱动必须唯一，且密钥字段只在服务端明文处理。

本表结构设计为首版开发基线。若后续引入第三方支付、订单体系、消息中心或多租户，需要新增独立模块表，不建议直接污染现有会员和系统设置表。
